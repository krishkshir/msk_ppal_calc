Fixing the share-link staleness check

A code-review finding from PR 4 (v0.4), deliberately left unfixed by that automated pass because the correct repair is a design decision, not a mechanical patch. This is that decision, written up before implementing it.

Implemented

Revision — the first implementation trusted unsigned data

The plan below originally called for displaying the frozen fee/ net/spread figures whenever they disagreed with a fresh recomputation, captioned as "what this link originally showed." A follow-up code review caught the flaw before it shipped further: those params are unsigned and fully attacker-editable — anyone holding the URL can set fee=1&net=99999 and the page would have rendered exactly that, with the app's own UI vouching for it as genuine. That is a strictly worse trust story than the bug this plan set out to fix, which could only ever show the output of a real settle() call for some (possibly attacker-chosen) input — never an arbitrary fabricated number. Every section below reflects the corrected, shipped design: frozen figures are used only to decide whether to warn, never to choose what's displayed. See "Trust boundary" below.

The bug

src/app/breakdown/page.tsx's resolve() (L22-39) re-runs settle() on every request from the link's frozen inputs only — gross, cur, mkt, fx.rate. The computed figures themselves are never frozen. The page's only drift signal is one string inequality (L102): 

resolved.shared.scheduleAsOf !== SCHEDULE_EFFECTIVE_FROM

v0.4 changed the calculation methodology without touching that date. SCHEDULE_EFFECTIVE_FROM is still "2026-05-28" (schedule.ts:18, byte-identical across the PR) — but the CAD fixed fee moved from FX-derived (the deleted resolveFixedFeeCents: roundHalfUpCents(fixedFeeUSDCents / fxBaseRateToUSD)) to a flat fixedFeeMinorUnits: 30 lookup in the new currencies.ts. A pre-v0.4 CAD share link — CA$1,000.00 at 0.73 USD/CAD — renders 66809 minor units received under the old math and 66818 under the new math. The client who already has that link open sees the new number with no warning at all, silently violating the v0.3 invariant that a shared link never quietly shows different figures. USD is unaffected — its fixed fee was always a direct lookup. Confirmed independently by a verifier agent during the PR 4 review.

Finding — the near-miss in v0.4's own plan

docs/plan-v0.4.html § "Minor units, because JPY has none" reasoned carefully about this exact link surface and concluded "share links keep decoding, only the TS field name changes" — correct about decodability, and entirely silent about numerical stability. The share-link contract was checked for whether old links still parse, never for whether they still compute the same answer.

The root cause: SCHEDULE_EFFECTIVE_FROM tracks PayPal's page date and SCHEDULE_LAST_REVIEWED_ON tracks our review date (schedule.ts § "Fee-table refresh workflow"). Neither one tracks our math. A PR can change how a figure is computed while both dates stay exactly where they were — which is precisely what happened here.

Decision — freeze the outputs, not a version number

Two designs were weighed. A hand-maintained CALC_METHODOLOGY_VERSION constant, bumped whenever the fee math changes and encoded in the link, is the smaller diff — but it reinstates exactly the discipline gap that caused this bug: it works only if a future PR remembers to bump it, which is the same failure mode as a stale schedule.ts date.

Decision — freeze the computed figures in the link, compare on open

Encode the amounts the link's owner actually saw at creation time, and on every open, recompute from the frozen inputs and compare. Any divergence — from any future cause, not just this one — trips the warning automatically. No constant for anyone to forget to update.

Trust boundary — frozen figures are a signal, never a source of truth

The frozen trio is unsigned data sitting in a URL query string, with nothing tying it to a genuine past settle() output — no server-side record, no signature, no secret. Anyone holding the link can edit it. So the comparison's result is used for exactly one thing: deciding whether to show a warning. The number actually rendered on screen is always this request's fresh settle() recomputation, regardless of drift. This gives up the "show the exact original quote" property the earlier draft of this plan wanted, but it's the only version of this feature that doesn't let anyone turn the client-facing breakdown into a forgery tool.

Finding — the trap that makes the naive version wrong

spread cannot be derived as gross − fee − net. commercialFee is denominated in payCurrency, while fxConversion and received are always USD (engine.ts:104, :135, :147). The identity gross = fee + net only holds when payCurrency === "USD" — for any FX case, fee and net aren't even in the same currency, so subtracting one from the other is meaningless. All three figures must be frozen independently; none can be reconstructed from the others.

{gross, fee, spread, net} is exactly the set that determines every number FeeBreakdown renders — verified against buildRows (fee-breakdown.tsx): the "converted to USD, before the spread" row is fxConversion.minorUnits + received.minorUnits (L86), and the fee bar's fill fraction is grossPaid.minorUnits − commercialFee.minorUnits (L55). Nothing else in the component reads a number that isn't derivable from this trio plus the existing gross.

Decode rules — src/lib/share/breakdown-link.ts

  • Add an optional group to SharedBreakdown (L11-19): frozen?: { feeMinorUnits: number; netMinorUnits: number; spreadMinorUnits?: number }. Optional is what preserves backward compatibility — the existing v0.3-era round-trip test (breakdown-link.test.ts L35-48, a link with no fee/ net/spread at all) must keep passing unchanged.
  • Treat the group atomically: fee and net present together, or both absent. A partial group is a decode error ("fee and net must both be present or both be absent"), so a half-tampered link fails loudly instead of half-verifying.
  • Validate fee/net/spread each as a non-negative integer, reusing the shape of the existing gross validator (L67-70).
  • Couple spread to fx exactly as fx/on are coupled today (L88-96): spread must be absent when cur === ACCOUNT_CURRENCY, present whenever fee/net are present and cur is not USD.
  • Extend encodeBreakdownParams (L42-54) to emit the trio when input.frozen is present.

Page logic — src/app/breakdown/page.tsx

  • In resolve(), keep the existing settle() call, then compare the recomputed commercialFee.minorUnits / received.minorUnits / fxConversion?.minorUnits against shared.frozen via hasFrozenDrift() (src/lib/share/drift.ts). Any difference sets a drifted flag.
  • The rendered breakdown is always the fresh recomputation — drifted only controls whether the warning paragraph appears, never which numbers are shown. There is no code path that displays shared.frozen's values. If settle() throws on the link's inputs, the page shows the same engine-error it always has — frozen figures are not used as a fallback source of truth, since there would be nothing to compare them against to establish they're genuine.
  • Warning precedence: when shared.frozen is present, output comparison is the sole drift signal and replaces the sched-date check for that link. This is strictly better, not just different — it drops today's false positive where PayPal's page date moves but no number actually changed for that transaction. The sched-date check is kept only as the fallback for links with no frozen group.
  • Adjacent copy bug, fixed in passing: the current legacy-path warning (L102-107) asserts "PayPal's rates have since been updated" from a bare !==, so it fires with that exact wording even when scheduleAsOf is newer than the deployed constant (a link created against a future-dated schedule opened on an older deploy). Reword to be direction-agnostic: state that the schedule dates differ, not that they moved in a particular direction.

Accepted limitations, recorded rather than hidden

  • confidence and note text still come from the current engine, not the link. These are methodology caveats, not amounts, and freezing prose into a URL is unreasonable. This is safe in practice because FeeBreakdown never renders the engine's own label field — buildRows hardcodes its own row labels (fee-breakdown.tsx:67, :99) — so the rate parenthetical baked into commercialFee.label can never appear on screen, stale or otherwise.
  • Pre-fix links carry no frozen group, so drift on them stays undetectable — confirmed as the user's explicit choice rather than a gap this plan papers over. That cohort is fixed in size (every link created before this ships) and shrinks to zero as old links age out of use.
  • A tampered net/fee/spread only ever produces a spurious warning (present or absent), never a wrong displayed figure — by the "Trust boundary" decision above, the displayed breakdown is always the fresh settle() recomputation, so a forged frozen value can make the page warn when it shouldn't (or stay silent when it should have warned, if someone forges figures that happen to match), but it can never make the page show a number that isn't a genuine engine output for the link's gross/cur/mkt/fx. That residual — a forged link can suppress or fake a warning — is accepted: it's strictly no worse than the original bug (silently wrong, no warning at all), and closing it fully would need signing infrastructure (a server-side secret, an API route) disproportionate to what a "not financial or legal advice" estimator warrants.

Verification

  • pnpm test — new cases in breakdown-link.test.ts: full round-trip with the frozen trio (USD and CAD); the v0.3-era link without the trio still decodes (backward compat, alongside the existing L35-48 case); partial-group rejection (fee present without net and vice versa); spread present with USD rejected; spread missing for non-USD rejected; negative/non-integer rejection for each of the three.
  • A regression test pinning the actual bug: decode a hand-written pre-v0.4-shaped CAD link carrying net=66809 (the old FX-derived figure), confirm a fresh settle() on its inputs yields 66818, and assert hasFrozenDrift() flags it. A companion test asserts a forged trio (fee=1&net=99999) also flags drift — confirming detection works without confirming or needing provenance, per the "Trust boundary" decision.
  • A structural-identity test asserting gross − fee === net for USD-only cases — kept as a test invariant rather than a decode-time validator, so decode logic stays simple and the assertion still catches a future engine change.
  • pnpm typecheck, pnpm build.
  • pnpm dev, then the claude-for-safari skill (new tab, screenshot, close the tab, delete screenshots when done) against: a freshly generated link (no warning); a link with a genuinely stale frozen trio (warning, but the recomputed figure renders, not the stale one); a link with a wildly forged trio like fee=1&net=99999 (warning fires, but the amount shown is still the genuine recomputation — confirms the forgery is inert); a legacy link with no trio (renders exactly as today, via the sched-date fallback).
