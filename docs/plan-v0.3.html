Implementing v0.3: the shareable client-facing breakdown

Proposal for the third roadmap milestone in docs/CONSTITUTION.md — a stateless, URL-encoded read-only page Ms. K can send a client, showing exactly where their payment went.

Proposed

Scope

CONSTITUTION.md gives this project two jobs, not one. v0.2 shipped the first — help Ms. K quote correctly. v0.3 is the second, and it's the one the originating complaint was actually about:

A new client from Canada finds it confusing cos it doesn't show him the transaction fee calculation but deducted it from me.

Today src/components/fee-breakdown.tsx's ledger exists only inside Ms. K's own calculator session. She has no way to hand a client the math, so a shortfall still reads as "she overcharged me" instead of "PayPal's cut, itemized." v0.3 closes that gap: a URL Ms. K can paste into an email or a chat message that renders a read-only, client-perspective breakdown of one specific payment — no login, no account, nothing stored server-side.

Per the roadmap, this is "Shareable client-facing breakdown (the transparency artifact)." The tech-stack table already committed to the mechanism: "Shareable breakdowns encode their inputs into the URL itself. No database, no stored client data, no accounts, no auth." This plan does not revisit that decision; it works out what has to be encoded, decoded, and rendered to make it real.

Explicitly out of scope, per the roadmap's own sequencing:

  • v0.4 — fee-table refresh workflow, broader currency/buyer-market coverage, resolving the two still-open questions in CONSTITUTION.md. v0.3 adds no new currencies and no new fee math; it only reuses settle() exactly as it exists today.
  • v1.0+ — PayPal API reconciliation.

src/lib/fees/{types,money,schedule,engine}.ts are not touched — the "fee engine is pure and isolated" design principle holds; v0.3 is a new consumer of the engine, exactly as v0.2 was.

Share URL format — readable query params, not an opaque blob

A shared breakdown needs six values, all of which are already inputs the calculator already collects or already fetched: the gross amount, the payment currency, the buyer market, the frozen FX rate and its date (currency conversions only), and the fee-schedule date the figures were computed under. 

/breakdown?gross=100000&cur=CAD&mkt=OTHER&fx=0.7312&on=2026-08-10&sched=2026-05-28
ParamMeaningNotes
grossGross paid, integer centsCents, not dollars — the engine is cents-native throughout; avoids locale/float parsing at the boundary
curUSD | CADThe engine's Currency union
mktUAE | EEA_UK | OTHERThe engine's BuyerMarket union
fxBase rate, USD per 1 unit of curOmitted when cur=USD; frozen at link-creation time, never re-fetched
onFrankfurter's rate dateOmitted when cur=USD
schedSCHEDULE_EFFECTIVE_FROM at link-creation timeLets the shared page detect and flag drift against today's schedule

This was weighed against an opaque encoded path segment (/breakdown/<base64url-json>, closer to what docs/plan.html's original file-layout sketch named) and decided against, with the user, in favor of plain query params: the payload here is roughly 60 characters, far too small for compression to buy anything, and this project's entire premise is transparency — a client should be able to look at the link and see, in plain text, exactly what numbers produced the breakdown they're reading. An opaque blob works against that.

Decision — the FX rate is frozen, never re-fetched

ECB reference rates move daily. If /breakdown called Frankfurter live on every view, the link Ms. K sends Monday would show different numbers on Wednesday than the invoice she actually issued — precisely the kind of silent mismatch this artifact exists to prevent. Freezing the rate into the URL at creation time also keeps the shared page a pure, zero-network render: no loading state, no fetch failure mode, nothing that can go stale mid-view.

Decision — no PII, and no calculator "mode" in the URL

The URL carries five numbers and two enums — no client name, no invoice reference, no free text, satisfying CONSTITUTION.md's "no PII is stored" non-goal by construction. Calculator mode (quote vs. settle) is deliberately not encoded either: a client-facing breakdown is always the settle view, and quote() already internally calls settle() at the rounded-up invoice amount, so breakdown.grossPaid.cents already is the invoice total regardless of which mode Ms. K used to get there. The share link reads it straight off whichever breakdown is on screen.

New module — src/lib/share/breakdown-link.ts

Encoding and decoding the URL is the only genuinely new logic in v0.3 — everything else downstream is reuse of existing, tested pieces. It belongs in its own pure module so it's covered by the existing Vitest environment: "node" setup, with no jsdom and no component-testing dependency added to the project. 

export interface SharedBreakdown {
  grossPaidCents: number;
  payCurrency: Currency;
  buyerMarket: BuyerMarket;
  fx?: { rate: number; asOf: string };   // absent iff payCurrency === "USD"
  scheduleAsOf: string;
}

export function encodeBreakdownParams(input: SharedBreakdown): string;   // → query string

export function decodeBreakdownParams(
  raw: Record<string, string | string[] | undefined>,
): { ok: true; value: SharedBreakdown } | { ok: false; reason: string };

Finding — no runtime validator exists yet for these unions

Currency and BuyerMarket are bare TypeScript unions in src/lib/fees/types.ts, with no runtime narrowing anywhere in the codebase — every existing call site controls its own values (a <select> in the calculator UI). A query string is untrusted input, so decodeBreakdownParams has to introduce the project's first runtime guards for these types: isCurrency / isBuyerMarket predicates, plus rejection of a non-integer or negative gross, a non-finite or non-positive fx, malformed on/sched dates, fx present alongside cur=USD, and fx missing alongside a non-USD cur. Every rejection path gets a named Vitest case, following engine.test.ts's existing convention of test names that state the claim being checked.

The shared page — src/app/breakdown/page.tsx

An async Server Component — no "use client", no hooks. Next.js 16 delivers searchParams as a promise, and the generated PageProps helper types the route by its literal path: 

export default async function Page(props: PageProps<'/breakdown'>) {
  const decoded = decodeBreakdownParams(await props.searchParams);
  // …
}

Reading searchParams opts the route into dynamic rendering, which is correct and free here — the page does no I/O of its own; every number it needs is already sitting in the URL.

The page has exactly three render states:

  1. Decode failure (missing, malformed, or tampered params) — a plain panel: "This breakdown link is incomplete or damaged," with a link back to /. Never a stack trace, never a hard crash — this is the one route a client, not Ms. K, might open.
  2. Engine throw — settle() already throws when the gross is smaller than the fixed fee it would incur. Wrapped in a try/catch reusing the exact same plain-language translation the calculator uses today (see below).
  3. Success — the ledger, an explainer, a disclaimer, and provenance, composed as follows.

Composition, top to bottom:

  • Header: eyebrow "Payment breakdown," a font-display headline, one line naming what the page is.
  • <FeeBreakdown breakdown topLabel="YOU PAY" receivedLabel="AMOUNT RECEIVED" /> — the existing, already server-safe, hook-free ledger component, reused as-is with client-perspective labels.
  • A 2–3 sentence explainer, conditional on whether an FX conversion applies — naming both deductions and why they compound when there's a currency conversion, or just the one when there isn't. This sentence is the actual point of the feature: it's the thing that turns "why did I get less than I sent" into "here's exactly why," in the client's own words, not fee jargon.
  • The estimate disclaimer, per CONSTITUTION.md's "estimates are labeled as estimates" design principle.
  • Provenance footer: fee-schedule date (already rendered by FeeBreakdown), plus the FX rate and its date, read from the URL.
  • Drift warning, shown only when the URL's sched no longer matches the engine's current SCHEDULE_EFFECTIVE_FROM — see below.
  • A quiet link back to /.

The confidence badges FeeBreakdown already renders (Observed / Estimated / Unvalidated) are kept exactly as-is on this page. On a client-facing view, an "Estimated" badge on the FX line isn't noise to hide — it's the honesty the constitution asks for, and it's already true today that no observed transaction involves a currency conversion, so that line item is always estimated regardless of who's looking at it.

The route also exports generateMetadata, returning a title like "Where your payment went — USD 669.14 received of CAD 1,000.00," so a pasted link previews meaningfully in chat and email clients. Generating an Open Graph image is out of scope for v0.3.

Immutability — what a stale link shows

A real failure mode: a client opens a link weeks after Ms. K sent it, by which point schedule.ts's fee figures have been corrected (as they were once already, from the previously-wrong 4.40% to the observed 4.625%). Three options were weighed with the user:

Decision — stamp the schedule date, recompute, warn on drift

The URL carries sched, the fee-schedule's effectiveFrom date at link-creation time. The page always recomputes via the current settle() — it never freezes the rate or fixed fee themselves into the URL, so the URL can't drift out of sync with the engine's schedule the way a fully-frozen link could. If the stamped sched no longer matches SCHEDULE_EFFECTIVE_FROM, the page adds one visible note: figures were computed under the schedule as of that earlier date, and PayPal's rates have since been updated, so the numbers shown reflect the current schedule. Honest about drift, without ever showing a client numbers Ms. K knows to be outdated.

Rejected: silently recomputing with no warning (an old link could then quietly disagree with the figure Ms. K actually quoted, with no indication why) and freezing every fee constant into the URL (most reproducible, but then the URL carries values that can drift out of sync with schedule.ts, and the shared page stops exercising the real schedule at all).

The share affordance — src/components/share-link.tsx

A small client component rendered on / only once a calculation has succeeded. It builds the share URL from encodeBreakdownParams plus window.location.origin, then offers:

  • A "Copy link to share with your client" button, using navigator.clipboard, with a brief "Copied" confirmation state.
  • A read-only text input showing the URL underneath, so the link is still obtainable if the clipboard API is blocked.

Decision — hand-roll, don't reintroduce shadcn's Button

Commit 94a3834 deliberately removed the unused shadcn Button component. This affordance follows src/components/mode-toggle.tsx's existing precedent instead — a plain <button> styled directly against the project's existing design tokens.

src/app/page.tsx gains one addition: <ShareLink> rendered inside the existing successful-calculation branch, passing the current breakdown and FX state. No other change to that file beyond the error-helper move above.
