Context

msk_ppal_calc is a greenfield repo (one untracked README.md, zero commits) with a git remote at krishkshir/msk_ppal_calc. The README captures the originating complaint verbatim:

A new client from Canada finds it confusing cos it doesn't show him the transaction fee calculation but deducted it from me.

Two distinct problems sit inside that sentence:

  1. Ms. K under-invoices. She quotes a number, PayPal deducts fees she can't predict, and she nets less than intended.
  2. The client can't see the math. PayPal shows the payer nothing about seller-side deductions, so the shortfall looks arbitrary — or worse, looks like Ms. K padded the bill.

The deliverable is CONSTITUTION.md: the project's mission, domain model, tech stack, and roadmap. The research below is the substance of that document — the fee mechanics are non-obvious and are the actual reason this project is hard.

Confirmed with the user: calculator only (no PayPal API integration), output serves both Ms. K and her clients, Next.js + TypeScript on Vercel, and the receiving account is UAE-registered, USD-denominated.

The finding that drives the whole design

The UAE account location is not a detail — it's the core constraint.

From PayPal's own UAE merchant fee schedule (last updated 2026-05-28), a UAE seller receiving payment pays:

Reconciling with Ms. K's current tool

Ms. K currently quotes her US-based clients using designhill.com's PayPal fee calculator. Its page copy is thin, so its actual JavaScript source was read directly rather than trusted at face value: 

var paypalPercentage = 3.4;
var paypalAddition = 0.30;
function setPapPalCommissionToolsPg(){
    var amt = parseFloat($("#amt").val());
    paypalPercentage = 4.4;
    if (amt >= 3000.01 && amt <= 10000)   paypalPercentage = 3.9;
    if (amt >= 10000.01 && amt <= 100000) paypalPercentage = 3.7;
    if (amt > 100000) paypalPercentage = 3.4;
}

This confirms the volume-tier table above — the fixed fee ($0.30) matches PayPal's own UAE fixed fee exactly, a real reconciliation point, not a coincidence. But the tool has two bugs this project deliberately does not inherit:

Bug 1 — wrong tiering basis

The tier is chosen by amt, the number typed into the tool's single input field — i.e. by the size of this one transaction, not by trailing monthly sales volume, even though the page's own copy describes it as a volume discount. A $15,000 invoice gets 3.7%; ten $1,500 invoices to the same client all get 4.4%. That isn't how PayPal's real volume discounts work.

Bug 2 — no currency modeling

One numeric field, implicitly USD. No country selector, no currency selector, no FX conversion anywhere in the code. Its "amount to ask for" reverse calculation is also not a clean closed-form inverse — it's a hand-rolled expansion that approximates it rather than solving it exactly. If this is the tool Ms. K used to quote the Canadian client, it silently drops the ~4% currency-conversion spread entirely — very plausibly the actual mechanism behind the original complaint, not PayPal's rules being confusing in the abstract.

Observed transactions (ground truth)

Three real, completed transactions are the project's first ground truth. All three are USD→USD, US-based clients — no currency conversion involved, so they isolate the commercial transaction fee from the 4% FX spread completely. This table is the validation set; append future observations here rather than starting a new one.

#Client paidMs. K receivedImplied feeEffective rate
T183.00 USD78.85 USD4.15 USD5.000%
T2101.20 USD96.21 USD4.99 USD4.931%
T3120.00 USD114.14 USD5.86 USD4.883%

Effective rate falls as the amount rises — the signature of a genuine fixed fee, confirming rate + fixed is the right model shape.

Out-of-sample validation: T1 and T2 alone solve to r = 4.615%, f = $0.319. That model, fitted without ever seeing T3, predicts T3's fee as 5.858 → 5.86. Actual: 5.86. A correct prediction on an unseen transaction is strong evidence the linear model is genuinely right, not curve-fitted.

Refit across all three (least squares): r = 4.622%, f = $0.313. The cleanest exact model, reproducing all three actual fees after cent-rounding, is 4.625% + $0.31:

ModelT1T2T3Verdict
4.40% + $0.30 (previously documented)3.95 ✗4.75 ✗5.58 ✗refuted
4.40% + $0.494.14 ~4.94 ✗5.77 ✗refuted
4.40% + $0.504.15 ✓4.95 ✗5.78 ✗refuted

4.625% + $0.314.15 ✓4.99 ✓5.86 ✓fits all three

Propagating ±half-cent rounding through the three-point solve gives feasible bands of rate 4.60–4.65% and fixed $0.29–$0.34. PayPal's published $0.30 fixed fee sits inside its band and is confirmed. The previously documented 4.40% rate falls well outside its band and is refuted — the first single observation (T1 alone) had suggested the fixed fee was the problem; with three points it's clear the opposite is true. That reversal is left in this document deliberately, as a record of why single-observation inference was resisted and why these tables stay provisional until confirmed.

Unexplained residual: the observed ~4.62% sits about 0.22 percentage points above PayPal's published "all other markets" rate of 4.40%, and is now too low to be explained by the 4.69% EEA/UK rate (both clients are US-based regardless). Something adds roughly a fifth of a percent that PayPal's UAE fee page doesn't document. Recorded as an open anomaly, not a conclusion — see open questions below.

Precision limit: these three transactions span only $37, which amplifies rounding noise into the ±0.025pp band above. One transaction at a substantially larger amount (~$500+) would tighten the rate band by roughly an order of magnitude.

Why Ms. K keeps coming up short

Because Ms. K is in the UAE and essentially every consulting client is abroad, the domestic 3.40% rate almost never applies. The realistic default case for a new client is the observed rate plus the conversion spread stacked on top: 

4.625%  (cross-border transaction fee — observed, not PayPal's published 4.40%)
+ USD 0.31  (fixed fee — observation-consistent with PayPal's published $0.30)
+ 4.0%  (currency conversion spread, if client didn't pay in USD)
─────────────────────────────────────────────
≈ 8.6–9.1% of the payment, gone before it reaches her

That compounding is exactly what blindsided the Canadian client. He sees "CAD 1,000 paid," Ms. K sees far less arrive, and nobody was shown the two-stage deduction. Making that visible is the product.

Open questions the document must record honestly

These are unresolved and materially change the math. CONSTITUTION.md will list them as open, not guess at them:

  1. Does Ms. K qualify for merchant-tier (volume-discounted) rates? PayPal offers reduced percentages above certain monthly volumes, granted on application. If she qualifies, every rate above changes.
  2. The fixed-fee table is incomplete for other currencies. The USD fixed fee is now observation-confirmed at $0.30 (see "Observed transactions" above). Fixed fees vary by settlement currency; the full table still needs filling in as more currencies are supported.
  3. Do the three untested volume tiers hold? The lowest tier (Ms. K's own) is now corrected against real data (4.625%, not 4.40%). The other three tiers (3.90%/3.70%/3.40%) are still sourced only from designhill.com's tool, which doesn't ask for seller country and may be applying a generic/US-style table regardless of where the seller is registered — and its lowest tier just turned out to be wrong. Treat all three as suspect until observed directly.
  4. Why does the observed rate (~4.62%) not match either of PayPal's published figures? It's about 0.22 percentage points above the published "all other markets" rate (4.40%), and now too low to be the EEA/UK rate (4.69%) — which wouldn't apply to US-based clients anyway. Resolution path: a transaction at a substantially larger amount (~$500+) would tighten the rate band by roughly an order of magnitude and confirm whether 4.625% holds at scale.

A prior open question about weekly USD→AED sweeping on withdrawal has been removed at the user's direction — out of scope for this project.

Recommended approach

Architecture principle

The fee engine is a pure, dependency-free TypeScript module with exhaustive unit tests, fully separate from UI and from network calls. The math is the product's entire credibility; it must be auditable in isolation and must not require a running browser or a live API to verify.

Two calculation directions, and they are not symmetric:

  • settle(grossPaid, buyerMarket, payCurrency) → what actually lands in USD
  • quote(netTarget, buyerMarket, payCurrency) → what to invoice to net the target

quote is the mathematically interesting one: it is not net / (1 - rate). The fixed fee and the FX spread apply at different points in the chain, so the inverse has to unwind them in the correct order. This is the primary target for test coverage, including a round-trip property test asserting settle(quote(n)) ≈ n.

Stack

  • Next.js (App Router) + TypeScript on Vercel
  • Tailwind + shadcn/ui
  • No database. Shareable breakdowns encode their inputs in a compressed URL param. No stored client data, no PII, no auth to build.
  • FX base rates: Frankfurter (https://api.frankfurter.dev/v2/rates?base=USD&quotes=CAD) — ECB reference rates, free, no API key, no account. Supplies the base rate only; PayPal's 4.0% spread is applied on top by the engine.
  • Vitest for the fee math.
  • No PayPal API integration in v1. Worth recording why in the document: PayPal exposes actual per-transaction fees via seller_receivable_breakdown (paypal_fee, net_amount, exchange_rate) but publishes no API for the fee schedule itself. Forward-looking estimates therefore require a hand-curated table regardless, so the API buys reconciliation, not prediction — a v2 concern.

Maintenance contract

Fee tables go stale silently, which is the failure mode that would quietly make this tool wrong. Every entry in schedule.ts carries an effectiveFrom date and its source URL; the UI surfaces "rates as of <date>"; the document commits to a quarterly review against PayPal's published schedule.

Design direction

For the shareable breakdown, the signature element is a vertical deduction ledger: a single column where a bar's length literally encodes the surviving money, shrinking down the page as each fee is subtracted. 

CLIENT PAYS
CAD 1,000.00                    ████████████████
  − cross-border  4.40%   44.00 ███████████████
  − fixed fee              0.42 ███████████████

YOU RECEIVE

It answers "where did my money go" in one glance, top-to-bottom like a receipt, and doubles as the artifact Ms. K sends the client. No pie charts, no stat tiles.
