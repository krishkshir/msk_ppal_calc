Plan · msk_ppal_calc · v0.5

Implementing v0.5: a transaction ledger that re-derives the fee model itself

Proposal to let Ms. K record real PayPal transactions herself, and have the app re-derive the commercial rate, fixed fees, and FX spread from them — proposing a change only when the data genuinely determines one, and otherwise saying so and keeping today's figures.

Proposed

Scope

Every figure the engine trusts today — 4.625% + $0.31 — was derived by hand from three transactions recorded in docs/CONSTITUTION.md. Adding a fourth observation today means editing a markdown table, redoing a regression by hand, and editing src/lib/fees/schedule.ts in a pull request. Ms. K is not technical, so in practice this never happens once the app ships, and the model silently ages exactly the way docs/plan.html's "Maintenance contract" warns against.

The roadmap already anticipates a version of this — v1.0+, "compare predicted fees against actual seller_receivable_breakdown data from completed transactions" — but that depends on a PayPal API endpoint that doesn't expose the fee schedule, only per-transaction results. v0.5 gets the same benefit by hand-entry: Ms. K records what a transaction actually paid and settled, and the app treats that the way CONSTITUTION.md's own "observed transactions" table already works — as a growing validation set the model must be reconciled against.

v0.5 — A gated ledger where Ms. K records real transactions; the app re-derives rate, fixed fees, and FX spread when the data uniquely determines them, and otherwise reports what's missing and leaves the current model in place.

Decisions confirmed with the user before drafting this plan:

  • Storage. A real, provisioned database — not localStorage (it would let the calculator and a shared /breakdown link disagree) and not an in-repo file (it would put a git commit on the critical path of Ms. K doing her job). Supabase, via the Vercel Marketplace, providing both the Postgres database and the login in one integration.
  • Two accounts. An admin account (the maintainer) and a user account for Ms. K, with different capabilities — see "Accounts and access" below.
  • Adoption is propose-and-confirm, never automatic. A re-derived model change only takes effect once explicitly accepted. Nothing displaces 4.625% + $0.31 silently.
  • Inference scope. The commercial rate and USD fixed fee (extending T1–T3's existing method), plus — new — each currency's fixed fee and the FX spread, both currently unvalidated/estimated with zero ground truth behind them.
  • Received currency stays USD. Ms. K holds a single USD PayPal balance; ACCOUNT_CURRENCY in schedule.ts remains a constant, not an input.
  • Ledger scope is a validation set, not bookkeeping. Append-only transaction records with the fields the solver needs, per the non-goal already stated in docs/CONSTITUTION.md. No invoicing, no totals, no client management.

Explicitly out of scope:

  • Re-deriving the UAE (3.4%) or EEA/UK (4.69%) rates — each needs its own transactions with a buyer in that market, and none exist yet. The schema records buyer country so this becomes solvable later without a migration.
  • PayPal API integration. This plan is the manual alternative to that roadmap item, not a step toward it.
  • Any bookkeeping, invoicing, or tax feature — the ledger's fields are the minimum the solver needs, not a business record.

The finding that shapes the whole design

Before designing the solver, the natural question is "does T1–T3 alone even determine a unique model?" — because if the seeded ledger already re-derives a different figure than 4.625% + $0.31, something is wrong before a single new transaction is entered. I ran the feasibility arithmetic directly: for every candidate integer fixed fee, each observation constrains the rate to an exact interval, and intersecting the three gives the fixed fee's feasible rate band.

Finding — T1–T3 do not uniquely determine the model

Six different integer fixed fees each admit a rate band that reproduces all three transactions exactly to the cent:

$0.324.6125% – 4.6196%
$0.334.6042% – 4.6084%
$0.344.5958% – 4.5964%

All six agree on T1–T3 by construction, and diverge outside that narrow range:

GrossPredicted fee, across all six modelsSpread
$83.00$4.150¢
$500.00$23.32 – $23.5220¢
$1,000.00$46.30 – $46.7545¢
$5,000.00$230.13 – $232.58245¢

4.625% + $0.31 is a defensible choice among the feasible models — the roundest rate that fits — not the unique solution. This is consistent with, not a contradiction of, CONSTITUTION.md's own note that the three transactions span only $37 and that "one $500+ transaction would tighten the rate band by roughly an order of magnitude."

Decision — judge uniqueness on predicted fees, not on the parameters

Asking "is (rate, fixed fee) unique?" will answer no forever, on any realistic amount of data — the feasible band only ever narrows, it doesn't collapse to a point. The solver instead asks whether every feasible model predicts the same fee, to the cent, across the amounts Ms. K actually invoices. That's answerable, and it's what she actually needs: a model good enough that which one is "true" stops mattering.

Consequence for the seed data: with only T1–T3 loaded, the ledger's status must read "confirmed, not yet uniquely determined" and propose nothing. That becomes the first and most important test of this feature — it is the one case a naive version of this feature gets wrong, by picking an arbitrary feasible model the moment two happen to differ.

The solver — src/lib/fees/solve.ts (new, pure, no I/O)

Exploits the same fact used above: fixed fees are integers in minor units, so roundHalfUp(gross · r + f) = fee constrains r to an exact interval for any candidate integer f. No curve-fitting library, no floating-point regression — exact interval arithmetic over a small integer sweep. 

fee = roundHalfUp(gross·r + f)
    ⟺  fee − 0.5 ≤ gross·r + f < fee + 0.5
    ⟺  (fee − 0.5 − f)/gross ≤ r < (fee + 0.5 − f)/gross

solveCommercial(observations: Observation[]): FeasibleModel[]
  // one entry per integer fixed fee whose rate-interval
  // intersection (across all observations) is non-empty

predictionSpread(feasible: FeasibleModel[], amounts: number[]): SpreadReport
  // for each amount, min/max fee predicted across the feasible set —
  // the uniqueness gate

solveConversion(observations, rate): ConversionResult
  // FX spread is global across currencies, so: sweep candidate
  // spreads on a fine grid, keep those where every currency in the
  // observations still admits ≥1 integer fixed fee

An empty feasible set means the observations contradict each other — most likely a mistyped amount, or (much less likely) a genuine mid-set PayPal rate change. Roughly 120 lines total, no new dependency.

Decision rules — src/lib/fees/propose.ts (new, pure)

SituationOutcome
Feasible set is emptyContradiction. Name the conflicting transactions. Keep the existing model.
Current model is still feasibleConfirmed, no proposal. Show the tightened band and "confirmed by N transactions."
Current model infeasible; predictions agree within tolerancePropose the new model for confirmation.
Current model infeasible; predictions disagreeRuled out, unresolved. Keep the existing model, say so plainly, name the transaction size that would resolve it.

Tolerance: predicted fees must agree to within one minor unit across a representative amount range, both as named constants with the reasoning in a comment alongside them. The last row is the case worth the most care — it's the one where adopting an arbitrary feasible model would be an easy, wrong shortcut.

FX needs a transaction's own date, not today's

src/lib/fx/frankfurter.ts today has no date parameter at all — it always hits the latest-rates endpoint. Verified against Frankfurter's own docs: the v2 API supports ?date=YYYY-MM-DD&base=…&quotes=USD, backed by ECB data to 1948, with no quota. A transaction's rate must be the rate on its payment date; using today's rate for a transaction from three months ago would poison the FX-spread solve with an unrelated market move.

Decision — add an optional date argument, existing call site untouched

getFxRateToUSD(payCurrency, date?). The existing no-argument call from src/app/page.tsx and its test in frankfurter.test.ts are unaffected. ECB publishes business days only, so the response's own date may precede the one requested — the ledger stores both and surfaces the gap rather than hiding it.

Finding — ECB mid-rate is not PayPal's base rate

Whatever spread the solver recovers from inference is the markup versus the public ECB reference rate, not literally PayPal's own (non-public) base rate — the two can differ for reasons that have nothing to do with PayPal's conversion fee. The ledger must label this "effective markup vs. ECB reference," not claim it as PayPal's published 4.0% MEA spread. When Ms. K can read PayPal's own displayed exchange rate off a transaction (the optional field below), the true spread is recoverable exactly, from a single transaction, with no ECB proxy involved.

Engine change — one optional field, everything else untouched

settle/quote in src/lib/fees/engine.ts currently read the rate, fixed fee, and FX spread from module-scope constants (selectTier, currencySpec, FX_SPREAD_RATE). The minimal change that lets a re-derived model flow through without touching either function's logic: 

interface CommonInput {
  // ...existing fields, unchanged...
  model?: FeeModel;   // { rate, fixedFeeMinorUnits, fxSpreadRate, confidence, asOf }
}

Absent, the engine builds the model from schedule.ts + currencies.ts exactly as it does today — so all 20 existing tests in engine.test.ts pass unmodified, and the same fallback path is what the calculator uses if the database is ever unreachable: it degrades to the committed constants rather than breaking. ratesAsOf becomes the active model's version identifier, which means SharedBreakdown.scheduleAsOf in src/lib/share/breakdown-link.ts and the drift check in src/lib/share/drift.ts keep working unchanged — and now catch a real case they were only built in anticipation of: a /breakdown link created before an accepted model change goes genuinely stale, and hasFrozenDrift() already flags it.

Accounts and access

Two Supabase accounts: an admin account for the maintainer, and a user account for Ms. K. /breakdown must stay publicly readable — clients open those links with no login — so gating is route-level on /ledger*, not Vercel deployment protection over the whole site.

Decision — Ms. K can accept a proposed model herself; the admin account can roll one back

Requiring admin sign-off on every acceptance would put a person back on the critical path this feature exists to remove. Instead, accepting is self-service, and fee_models is append-only — accepting supersedes the previous row rather than deleting it — so any accepted model can be reverted from an admin-only history view. The cost is asymmetric but bounded: a bad model can reach clients before it's noticed, but it can always be undone, and every prior state stays on the record.

Raw diagnostics are admin-only so Ms. K's view stays a plain-language read — "your transactions confirm the current rate" or "3 new transactions rule out the current rate; sent for review" — rather than a page of intervals only useful for auditing the model, which is the admin's job. Transaction correction, T1–T3 edits, and rollback are admin-only because each is a data-quality judgment call of exactly the kind that originally produced 4.625% + $0.31 — deciding whether a surprising number is real or a mistake.

Row-level security:

  • fee_models is anon-readable — the public calculator and /breakdown both need the active model, and the rate itself isn't a secret — but write access requires an authenticated session with an accepted proposal, enforced at the application layer above the DB write.
  • transactions is authenticated-only in both directions; policies further split write access to excluded_reason, T1–T3 rows, and fee_models inserts to role = 'admin' per the capability table above.

Seed transactions with T1–T3 exactly as recorded in docs/CONSTITUTION.md, and fee_models with today's 4.625% + $0.31 / 4.0% row, accepted at SCHEDULE_EFFECTIVE_FROM. Seeding must reproduce today's calculator output exactly — the first verification step below.

The ledger status panel

This is the part of the UI that carries the feature — it should read like a lab result, not a settings page. It states: what the current model is and whether the transactions confirm it; the feasible band and the fee spread it implies at representative amounts (full detail for admin, plain language for Ms. K, per the capability split above); when undetermined, the transaction size that would most tighten it, directly actionable and already implied by CONSTITUTION.md's own "$500+ would tighten the band by an order of magnitude" note; and when contradicted, exactly which transactions disagree.

Follows this repo's existing conventions: hand-rolled controls in the style of calculator-form.tsx (only Input and Label exist under components/ui/ — no shadcn Select/Table pulled in), the globals.css palette, and fee-breakdown.tsx's confidence-badge idiom for showing observed / estimated / unvalidated. Built via the /frontend-design:frontend-design skill per CLAUDE.md.

Known limitations to record, not hide

  • Cross-currency inference is proxy-limited. The FX spread solved from inference is measured against ECB mid, not PayPal's own base rate — see "FX needs a transaction's own date" above. Labeled as such everywhere it's shown.
  • A bad model can go live before the admin notices. The direct cost of letting Ms. K accept a proposal herself; mitigated, not eliminated, by append-only history and admin rollback.
  • Per-market rates stay unvalidated. UAE and EEA/UK need their own transactions before they're solvable at all; this plan doesn't get her there, only makes it possible later.
  • CONSTITUTION.md's unexplained ~0.22pp gap between the observed 4.625% and PayPal's published 4.40% stays unresolved, per the user's standing direction — this plan doesn't touch it, and nothing here should be read as resolving it.

Execution order

  1. docs/plan-v0.5.html — this document.
  2. solve.ts + propose.ts with tests, pure and entirely offline — no database, no UI. Locks the math before any infrastructure exists.
  3. vercel integration add supabase; migrations; seed T1–T3 and the current model.
  4. Auth (magic link) and gated /ledger* routes, admin/user role split.
  5. Thread model through the engine; / and /breakdown read the active model.
  6. Ledger UI — status panel, entry form, accept/reject.
  7. Docs.

Steps 1–2 are independently valuable and carry essentially all of the mathematical risk; if Supabase provisioning stalls for any reason, the solver still stands on its own and can be reviewed and tested in isolation.
