Implementing v0.2: the calculator UI

Proposal for the second roadmap milestone in docs/CONSTITUTION.md — a Next.js calculator wired to the v0.1 fee engine, for Ms. K's own use.

Proposed

Scope

Per the roadmap, v0.2 is "Calculator UI: both directions, for Ms. K's own use." v0.1 already shipped the fee engine — src/lib/fees/{types,money,schedule,engine}.ts, 19 passing Vitest tests, no UI, no network call (fxBaseRateToUSD is an injected parameter). v0.2 wires that existing, untouched engine to a Next.js UI. It does not touch src/lib/fees/* — the design principle "the fee engine is pure and isolated" holds; the UI is a consumer of it, not a collaborator.

Explicitly out of scope, per the roadmap's own sequencing:

  • v0.3 — the shareable, URL-encoded client-facing breakdown. v0.2 is for Ms. K's own use only; nothing gets shared with a client yet.
  • v0.4 — broader currency and buyer-market coverage. The engine's Currency union stays exactly "USD" | "CAD"; the 22 other currencies now listed in CONSTITUTION.md § "Fixed fee by currency (published)" are not wired up yet — they're unvalidated by observation regardless.
  • v1.0+ — PayPal API reconciliation.

Scaffold & stack

Next.js (App Router) + TypeScript on Vercel, Tailwind + shadcn/ui — all already decided in CONSTITUTION.md § "Tech stack," not re-litigated here. src/lib/fees/ moves into the new tree unchanged; the existing pnpm test / pnpm typecheck scripts keep working exactly as they do today.

Implementation-time, not fixed here

Exact Next.js / Tailwind / shadcn scaffold commands and config are verified via context7 at implementation time, per CLAUDE.md § "Tool usage" — these drift across versions and shouldn't be hardcoded into a plan document.

FX integration — src/lib/fx/frankfurter.ts

An isolated fetch module, imported by the UI only — never by engine.ts. Fetches the base USD→CAD market rate from Frankfurter, plus its own "as of" date.

Decision

Don't extend Breakdown to carry the FX rate's date — thread it through UI state separately instead, so the pure engine's return type stays untouched. The UI shows two independent captions: "fee schedule as of SCHEDULE_EFFECTIVE_FROM" and "FX rate as of <Frankfurter's date>," matching the "every number is dated and sourced" design principle without an engine schema change.

Calculator UI — src/app/page.tsx

A single page with a mode toggle between the engine's two directions:

  • Quote ("what do I invoice to net my target") — default/first, matching the mission's job ordering (job 1: help Ms. K quote correctly; job 2: make the deduction visible).
  • Settle ("what will I actually receive") — second.

Inputs:

  • Amount
  • Buyer market — UAE / EEA & UK / all other markets, default "all other markets" (Ms. K's practical case, per "Why Ms. K keeps coming up short")
  • Payment currency — USD / CAD, default USD, matching the engine's current Currency union exactly

Decision — no trailing-volume input

CLAUDE.md's domain-model notes say directly: "Don't build UI or logic that assumes she might reach those [higher-volume] tiers without this being revisited." Merchant-tier ineligibility is resolved (confirmed with the user), so monthlyVolumeUSDCents is hardcoded to 0 internally — there is no monthly-volume field in the UI at all.

Output: the vertical deduction-ledger design already recorded in docs/plan.html § "Design direction" — navy/paper/oxide-red/teal/brass tokens, Fraunces for the display figure, IBM Plex Sans for body, IBM Plex Mono for every number. Each fee line item's confidence (observed / estimated / unvalidated) is surfaced as a visible badge, not just computed — per "estimates are labeled as estimates."

Implementation-time, not fixed here

Final visual/UX execution (exact component layout, spacing, shadcn primitives chosen) must automatically invoke /frontend-design:frontend-design, per CLAUDE.md § "Tool usage." This plan fixes the content and data requirements — what must be shown and why — not final pixel decisions.

Deployment

CONSTITUTION.md's tech-stack table already decided Vercel hosting ("zero-config deploy, free tier is sufficient"), and the mission frames Ms. K as non-technical — the README's originating request opens with "I'm not the best at this." A locally-run dev server doesn't satisfy "for Ms. K's own use." This plan proposes v0.2 includes an actual Vercel preview deployment, using the vercel skills already available in this environment, as part of verification — not just pnpm dev.
