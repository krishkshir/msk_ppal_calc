Implementing v0.1: the fee engine

Proposal for the first roadmap milestone in docs/CONSTITUTION.md — a pure, tested settle/quote engine. No UI, no network call.

Proposed

Scope

Per the roadmap, v0.1 is the fee engine and its test suite — nothing more. No calculator UI (v0.2), no shareable breakdown (v0.3), no FX network call. The Frankfurter base rate is an injected parameter, not a fetch: src/lib/fx/frankfurter.ts is named here as a v0.2 concern so the engine stays pure per CONSTITUTION.md § "Design principles" — no UI dependency, no network call inside the math itself, testable and auditable on its own.

Named regression cases from the roadmap: T1 (83.00 → 78.85), T2 (101.20 → 96.21), T3 (120.00 → 114.14), plus the README's Canadian scenario — flagged distinctly, since it has no ground truth of its own.

A contradiction found while planning

CLAUDE.md states the corrected fee model as 4.625% + $0.30. That pair reproduces none of the three ground-truth transactions:

ModelT1 (83.00)T2 (101.20)T3 (120.00)
4.625% + $0.304.14 ✗4.98 ✗5.85 ✗
4.625% + $0.314.15 ✓4.99 ✓5.86 ✓
4.635% + $0.304.15 ✓4.99 ✓5.86 ✓

Each figure is individually inside its own feasible band (rate 4.60–4.65%, fixed $0.29–$0.34 per CONSTITUTION.md's three-point solve), but 4.625% and $0.30 are not jointly feasible — together they undershoot every observation by a cent. This was already a latent inconsistency in the docs: CONSTITUTION.md's tier table said $0.30 (observation-confirmed) while its own derivation section and "Why Ms. K keeps coming up short" block both said $0.31.

Decided

Encode 4.625% + $0.31 — the pair CONSTITUTION.md's own derivation concludes fits all three. CLAUDE.md and CONSTITUTION.md's tier table have been corrected to match, in the same change as this plan.

Since v0.1's regression tests are T1–T3, this had to be settled before the engine could be designed, not discovered after.

Module layout

Minimal TypeScript + Vitest only — no Next.js, Tailwind, or shadcn until v0.2 has UI to build. Paths match those already declared in docs/plan.html, so the later Next.js scaffold wraps this tree without moving anything.

Money is held as integer cents, never floats — the model is validated at cent precision in CONSTITUTION.md, and float drift would silently break the regression cases. Rounding is nearest-cent, half-up; the observations confirm nearest but can't distinguish tie-breaking, so that's documented in money.ts as an assumption, not a fact.

The two directions

Not symmetric — per CONSTITUTION.md § "Design principles", quote is not net / (1 - rate), because the fixed fee and the FX spread apply at different points in the chain.

settle(grossPaid, payCurrency, buyerMarket, monthlyVolumeUSD, fxBaseRate)

→ what actually lands in USD:

  1. Select tier by trailing monthlyVolumeUSD — never by this transaction's size
  2. commercialFee = round(gross × rate + fixed), in the payment currency
  3. netInPayCurrency = gross − commercialFee
  4. If cross-currency: received = round(netInPayCurrency × fxBaseRate × (1 − 0.04))

quote(netTargetUSD, payCurrency, buyerMarket, monthlyVolumeUSD, fxBaseRate)

→ what to invoice to net the target — unwound in reverse order:

  1. netInPayCurrency = netTargetUSD / (fxBaseRate × (1 − spread))
  2. gross = (netInPayCurrency + fixed) / (1 − rate)
  3. Round up to the cent, so Ms. K never comes up short of her target

Cent rounding makes an exact round-trip impossible, so the property test states settle(quote(n)).received >= n (within a couple of cents above), not ≈ n — an honest bound rather than a fudged equality.

Every Breakdown line item carries a confidence (observed / estimated / unvalidated) and the result carries a ratesAsOf date — pushing "these are estimates" into the data layer so v0.2's UI can't forget it, per CONSTITUTION.md's "estimates are labeled as estimates" principle.

FX order of operations — flagged assumption

The Canadian scenario has no ground truth. The engine assumes PayPal's documented behaviour — fee first, in the payment currency, then convert: the commercial fee (and its own currency's fixed fee) is deducted from the gross CAD amount, and only the remainder is converted to USD at base × (1 − 4%).

Assumption, not observation

This order is not derived from any transaction Ms. K has provided — T1/T2/T3 are all USD→USD and can't distinguish it from "convert first, then fee." It's the documented PayPal behaviour, but it ships as confidence: "estimated" on the FX line item, and the Canadian-scenario test is named to say so explicitly. It also implies a non-USD (CAD) fixed fee, which open question #2 in CONSTITUTION.md already flags as unresolved — the engine estimates it rather than inventing false precision.

Test suite

The engine's credibility is the entire product, so coverage is exhaustive by design:

  • Named regression: T1, T2, T3 asserted to the exact cent
  • Refutation guard: assert that 4.40% + $0.30 and 4.625% + $0.30 do not reproduce T1–T3 — makes CLAUDE.md's "don't revert to the published figure" warning executable, so a future well-meaning "fix" fails loudly instead of silently reintroducing the error
  • Tiering-basis test: one $15,000 transaction at monthlyVolumeUSD = 0 uses the lowest tier; ten $1,500 transactions at trailing volume $15,000 use the $10k–$100k tier — proves the designhill single-transaction-size bug is not reproduced
  • Round-trip property: settle(quote(n)).received >= n swept across $1–$10,000
  • Monotonic effective-rate check: effective rate falls as the gross amount rises — the signature that originally confirmed rate + fixed was the right model shape
  • Canadian scenario from the README, test title stating explicitly that it has no ground truth and is asserted only against the engine's documented FX-order assumption
  • Schedule metadata: every table entry has effectiveFrom, sourceUrl, and confidence set

Open questions carried forward, not resolved

Per CONSTITUTION.md: none of these block v0.1, but none get silently decided either — each surfaces as a confidence flag in schedule.ts rather than a hardcoded fact.

  1. Merchant-tier eligibility — unknown whether Ms. K qualifies for volume-discounted rates.
  2. Non-USD fixed fees — only USD is observed ($0.31); other currencies' fixed fees are estimated, not sourced.
  3. The three untested volume tiers (3.90%/3.70%/3.40%) — sourced only from designhill.com, unvalidated by observation, marked confidence: "unvalidated".
  4. The ~0.22pp residual between the observed 4.625% and PayPal's published 4.40% — recorded, not explained.
