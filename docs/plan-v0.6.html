Plan · msk_ppal_calc · v0.6

Implementing v0.6: a rates & fees table on the ledger, with named provenance and manual overrides

Proposal to show every rate and fee the engine actually uses — one row per buyer-market tier, per currency's fixed fee, and the FX spread — labeled with exactly where each figure came from (PayPal's own page, a third-party tool, or computed by this app) and the date it took effect, to both user and admin accounts on /ledger. Both accounts can also type in a corrected figure as a dated manual override, which takes effect immediately on the public calculator and every new /breakdown link.

Proposed

Scope

The figures the engine trusts today are already dated and already sourced — ScheduleEntry (src/lib/fees/schedule.ts) and CurrencySpec (src/lib/fees/currencies.ts) both carry a sourceUrl, an effectiveFrom, a confidence, and a note on every row. None of it reaches the screen. sourceUrl and effectiveFrom are read by nothing in the app; note only ever surfaces as a title= tooltip (src/components/fee-breakdown.tsx's ConfidenceBadge). /ledger itself goes further: loadLedgerStatus() (src/app/ledger/status.ts) already returns the active ledger-derived model, and src/app/ledger/page.tsx discards it without rendering a single field.

Two things are missing beyond rendering what already exists:

  • Origin is not the same axis as confidence. Confidence (observed / estimated / unvalidated) says how much to trust a number. It says nothing about where the number came from — PayPal's own published page, a third-party tool, or something this app computed. Today that's only recoverable by string-matching a sourceUrl against a hardcoded constant no UI reads.
  • No figure can be corrected without a code deploy. Every non-USD fixed fee is unvalidated: PayPal's published table (currencies.ts) or a designhill-sourced volume tier (schedule.ts) can go stale the moment PayPal changes a published number, and today fixing it means a pull request. Ms. K should be able to type the right figure in directly.

Decisions confirmed with the user before drafting this plan:

  • An override changes real calculations, not just the ledger display. Precedence, highest wins: a manual override beats the accepted ledger model (fee_models), which beats the static table (schedule.ts / currencies.ts). The public calculator at / and every newly generated /breakdown link pick up an override immediately.
  • An override carries two dates. A person-supplied effective from — the date the figure actually took effect, e.g. the date PayPal changed a published number — plus an app-stamped set by / set on, so a figure's real-world date and its audit date are both visible and never conflated.
  • On conflict with the ledger's own solver, the override wins, with a visible warning. If Ms. K's recorded transactions later determine a different commercial rate or fixed fee than a figure someone typed in, the override stays in force — nothing changes what a client is quoted silently — and the status panel says plainly that a manual override is masking what the transactions determine, with a one-click way to clear it. Accepting a solver proposal never wipes an unrelated override out from under whoever set it.
  • Both roles get the same override capability. Unlike excluding a transaction or reverting a model (admin-only, per docs/plan-v0.5.html "Accounts and access"), correcting a published rate or fee is not a data-quality judgment call about the ledger's own evidence — it's Ms. K noticing PayPal changed a number on its website. user and admin are equal here.

Origin, as data — src/lib/fees/sources.ts (new, pure)

A small named registry, so "where did this number come from" is a lookup, not a URL pattern-match: 

export type SourceKind = "published" | "third-party" | "derived" | "manual";
export interface FeeSource { kind: SourceKind; label: string; url?: string }

export const FEE_SOURCES = {
  paypalMerchantFees:   { kind: "published",   label: "PayPal — UAE merchant fees",
                           url: "https://www.paypal.com/ae/webapps/mpp/merchant-fees" },
  paypalBusinessFees:   { kind: "published",   label: "PayPal — Business fees (AE)",
                           url: "https://www.paypal.com/ae/business/paypal-business-fees" },
  designhillCalculator: { kind: "third-party", label: "designhill.com PayPal fee calculator",
                           url: "https://www.designhill.com/tools/paypal-fee-calculator" },
  observedTransactions: { kind: "derived",     label: "Computed by this app from T1–T3",
                           url: "../docs/CONSTITUTION.md#observed-transactions-ground-truth" },
  ledgerModel:          { kind: "derived",     label: "Computed by this app from your ledger" },
  manualOverride:       { kind: "manual",      label: "Manual override" },
} as const satisfies Record;

export type FeeSourceId = keyof typeof FEE_SOURCES;
export function feeSource(id: FeeSourceId): FeeSource;

ScheduleEntry.sourceUrl and CurrencySpec.sourceUrl are replaced with sourceId: FeeSourceId, and the five module-private URL constants currently duplicated across schedule.ts and currencies.ts move into this one file. Mechanical across the 6 schedule rows and 23 currency rows, and safe to do — sourceUrl has no readers today, verified by search. Mapping: the UAE and EEA/UK tiers plus FX_SPREAD_RATE → paypalMerchantFees; the three higher OTHER volume tiers → designhillCalculator; the OTHER $0–$3,000 tier and USD's $0.31 → observedTransactions; all 22 non-USD fixed fees → paypalBusinessFees. ledgerModel covers any live fee_models row — the seed row's own note already records that it came from T1–T3, so no new column is needed to tell a seeded row from a solver-accepted one apart.

Override targets — src/lib/fees/overrides.ts (new, pure)

"Any rate and fee in the displayed table" spans three shapes: a commercial rate for one buyer-market tier, one currency's fixed fee, or the single FX spread. A generic keyed target, not new columns bolted onto fee_models, because fee_models.rate structurally can't express a UAE or EEA/UK rate — resolveFeeModel (src/lib/fees/model.ts:72) applies it to the OTHER market only.

export interface Override {
  targetKey: string;
  value: number;              // rate as a fraction; fixed fee/spread in integer minor units
  effectiveFrom: string;      // YYYY-MM-DD, person-supplied
  setByEmail: string | null;
  setAt: string;              // app-stamped

ActiveOverrides is a plain readonly array, not a Map: src/components/calculator.tsx is a client component that receives its model as a prop from the server component at src/app/page.tsx, so this value crosses the RSC serialization boundary and has to stay trivially serializable, the same reasoning ActiveFeeModelRow already follows.

Storage units mirror the rest of the fee engine: rates as fractions, fixed fees as integer minor units. The server action converts what a person actually types using currencySpec(currency).minorUnitExponent, so JPY's exponent-0 trap (CLAUDE.md § "Domain model" — a plain minor-unit multiply is off by a power of ten for any currency whose exponent isn't 2) is handled in exactly one place, not re-derived per call site. Validation: rate and spread values in [0, 0.5]; fixed fees an integer in [0, 1_000_000] minor units; effectiveFrom a real calendar date, not in the future — a figure can't already be in force from a date that hasn't happened, and nothing in this design filters by date at read time, only at display and audit time.

Schema — supabase/migrations/20260812000000_fee_overrides.sql

Append-only, matching fee_models' own philosophy (supabase/migrations/20260810160000_v0_5_ledger.sql): no UPDATE policy and no DELETE policy, so RLS denies both outright at the database, not just by app-layer convention. Clearing an override inserts a tombstone row (cleared = true, value null) rather than deleting history — the same reasoning that makes excluding a transaction, not deleting it, this project's standing rule.

  • target_key text not null with a format check constraint; value numeric, cleared boolean not null default false, and a table check that exactly one of the two is meaningfully set.
  • effective_from date not null, note text, set_at timestamptz not null default now(), set_by uuid references auth.users(id), set_by_email text.
  • set_by / set_by_email are stamped by a SECURITY DEFINER before-insert trigger reading auth.uid(), overwriting whatever the client sent — the same pattern the ledger-access-lockdown work established for deriving identity server-side (supabase/migrations/20260811120000_derive_ledger_access.sql) rather than trusting a form value. No client can spoof who typed a figure, and no with check (set_by = auth.uid()) is needed on the insert policy.
  • Index (target_key, set_at desc) — every read wants the newest row per target.
  • SELECT is public but column-restricted. The calculator at / and /breakdown both need to read overrides with no login, the same reasoning fee_models' deliberately anon-readable SELECT policy already documents. But an override's set_by_email must not become a publicly readable list of ledger members' email addresses. Row-level security alone can't restrict that — it's a column, not a row — so this uses Postgres column-level grants underneath a permissive RLS policy: 
    revoke select on public.fee_overrides from anon;
grant select (id, target_key, value, cleared, effective_from, note, set_at)
  on public.fee_overrides to anon;
grant select on public.fee_overrides to authenticated;  -- full row, incl. set_by_email
  • INSERT is authenticated-and-member only: to authenticated with check ( (select public.is_ledger_member()) ) — the exact pattern already used for fee_models inserts in supabase/migrations/20260811090000_allowed_accounts.sql:193, deliberately not role-gated: both user and admin are trusted, already-authenticated accounts of a two-person app, and the user's confirmed decision is that both roles can set an override.

Precedence — src/lib/fees/model.ts and engine.ts

resolveFeeModel(row, buyerMarket, payCurrency) gains a fourth, defaulted argument: 

export function resolveFeeModel(
  row: ActiveFeeModelRow | null,
  buyerMarket: BuyerMarket,
  payCurrency: Currency,
  overrides: ActiveOverrides = [],
): FeeModel | undefined

Overrides are applied after the ledger row is resolved, so they win — a rate override replaces row.rate-derived value, a fixed-fee override replaces row.fixedFeeMinorUnits / row.perCurrencyFixedFees[currency], an FX-spread override replaces row.fxSpreadRate. The rate target's key resolves through selectTier(buyerMarket, 0) — the same hardcoded-zero trailing volume every existing call site already uses, per that function's own doc comment, since Ms. K's practical tier never varies by volume (CLAUDE.md § "Domain model"). Critically, an override on a UAE or EEA/UK rate does apply — unlike fee_models.rate, which resolveFeeModel only ever applies to the OTHER market (line 72, unchanged), a manual override is scoped to whichever tier it names, so this is also how UAE/EEA_UK rates become correctable at all, something v0.5 explicitly left unsolvable.

When an override contributes to a field: confidence for that field becomes the new "manual" value (added below), and asOf becomes the later of the override's effectiveFrom and whatever the ledger model's asOf already was.

Decision — add a fourth Confidence value, don't repurpose an existing one

Confidence (src/lib/fees/currencies.ts) gains "manual" alongside observed / estimated / unvalidated. Reusing observed would conflate "this is ground truth from a real transaction" with "someone typed this in" — two very different epistemic states this project has been careful to keep distinct since v0.1's refutation of PayPal's published 4.40%. src/components/fee-breakdown.tsx's ConfidenceBadge gets a fourth label/class pair ("Overridden", an ink-toned badge — estimated already owns brass, unvalidated already owns oxide). engine.ts's confidenceFor() needs no change: it only ever downgrades "observed" to "estimated" for a non-USD static fixed fee, so "manual" passes through it untouched. fee_models.confidence's database check constraint stays three-valued — "manual" is a display/engine concept, and it never gets written into a fee_models row.

engine.ts gets one added branch in commercialFee.note (and the analogous spot for fxConversion.note) naming the override and its effective date, alongside the existing static-schedule and ledger-model note branches. Because ratesAsOf already moves whenever the resolved model's version changes, an override correctly triggers the existing share-link drift warning (src/lib/share/drift.ts's hasFrozenDrift()) for any /breakdown link generated before it — no change needed there.

Every call site that fetches the active model must also fetch and pass overrides: src/app/page.tsx (then through to src/components/calculator.tsx's existing resolveFeeModel call), src/app/breakdown/page.tsx (both generateMetadata and the page body), and src/app/ledger/status.ts.

The table — src/lib/fees/rate-rows.ts (new, pure) + src/components/ledger/rates-table.tsx

One pure function resolves provenance for every row, independent of any database call, so it's unit-testable without Supabase: 

export interface RateRow {
  targetKey: string;
  target: OverrideTarget;
  label: string;        // "Rest of world · $0–$3,000" | "CAD — Canadian Dollar" | "Currency conversion spread"
  display: string;      // "4.625%" | "$0.31" | "4.0%"
  source: FeeSource;
  effectiveDate: string;
  setBy?: string;
  setAt?: string;
  baseline?: { display: string; source: FeeSource; effectiveDate: string };  // masked figure, if overridden
  note?: string;
  applicable: boolean;  // false for the volume tiers Ms. K doesn't qualify for
}

export function buildRateRows(
  activeModel: ActiveFeeModelRow | null,
  overrides: ActiveOverrides,
): RateRow[];

Three sections on /ledger, in one new panel below the existing status panel: Commercial rate (one row per SCHEDULE entry — the three higher OTHER volume tiers render with applicable: false and a "not applicable — Ms. K doesn't qualify for volume discounts" caption, per CLAUDE.md § "Domain model"), Fixed fee per currency (23 rows, USD first), and Currency conversion spread (one row).

Columns: Parameter, Value, Where it comes from, As of, and an override control. The source column links out (target="_blank" rel="noopener noreferrer") for published / third-party kinds; a derived row shows "Computed by this app" plus that model's own note; a manual row shows "Manual override · set by email on date" with the masked baseline value rendered underneath it, using the same ConfidenceBadge idiom fee-breakdown.tsx already establishes.

The override control is a native <details> disclosure per row, wrapping a plain server-action <form> (a value input prefilled with the current figure, an effective from date input, an optional note, Save — plus a Clear button when an override is already active). No client component: every file under src/app/ledger/ is a server component today, and this keeps that true with zero client JS for what would otherwise be ~30 editable rows.

Reuses isScheduleReviewOverdue(new Date()) (src/lib/fees/schedule.ts:43) for a staleness banner above the table — it currently has exactly one consumer, src/components/calculator.tsx, and this table is its natural second home on /ledger, which today shows no staleness signal at all.

Server actions — src/app/ledger/actions.ts

setOverrideAction and clearOverrideAction, both gated with requireUser("/ledger") — not requireAdmin, per the confirmed decision that both roles can override. Each re-derives the target with parseTargetKey against the real SCHEDULE and CURRENCIES tables and rejects anything that doesn't resolve — form fields are attacker-editable, the same guard acceptProposalAction and revertToModelAction already apply by re-reading server-side rather than trusting a posted value. On success, revalidatePath for /ledger, /, and /breakdown, matching acceptProposalAction's existing revalidation set exactly. On failure, redirect to /ledger?error=bad_override, rendered by the same banner pattern already at src/app/ledger/page.tsx:53 for not_admin.

The masking warning — src/components/ledger/status-panel.tsx

When an override exists on rate:OTHER:0, fixedFee:USD, or fxSpread — the three targets the solver in src/lib/fees/propose.ts can actually reach a verdict on — and that target's verdict is confirmed or propose, the relevant status-panel section shows both figures side by side with the sentence "a manual override is masking what your transactions determine," plus an inline Clear button reusing clearOverrideAction. acceptProposalAction itself is left untouched — accepting a solver proposal never clears an unrelated override, per the confirmed decision that nothing changes a typed-in figure silently.

Tests

  • src/lib/fees/overrides.test.ts — targetKey / parseTargetKey round-trip; parsing rejects an unknown market, an unknown currency, a tier bound that doesn't match SCHEDULE, and a malformed key; value-bound checks; the JPY conversion case (typing 40 into the fixed-fee field yields 40 minor units, not 4000).
  • src/lib/fees/rate-rows.test.ts — the full precedence ladder (static → ledger model → override) at every level; a cleared override correctly falls back to whatever's beneath it; and a coverage guard: every SCHEDULE and CURRENCIES entry produces exactly one row with a resolvable FeeSource, so adding a currency later without a source mapping fails this suite instead of silently rendering nothing.
  • src/lib/fees/model.test.ts — resolveFeeModel with overrides present: resolved confidence is "manual", asOf is the override's effective date, and — the case v0.5 couldn't reach — a UAE or EEA/UK rate override actually applies, where a fee_models row on its own does not.
  • src/lib/fees/engine.test.ts stays unmodified. That it keeps passing unmodified is itself the regression guard proving the no-override path is byte-identical to v0.5 — exactly the discipline v0.5's own plan applied to its 20 pre-existing tests.

Known limitations to record, not hide

  • An override is a flat current value, not a time series. effective_from is recorded and displayed, but nothing in this design recomputes an old transaction against whichever figure was actually in force on its own date. Stated plainly in the UI, not solved here.
  • A typo'd override silently changes what a client is quoted. The mitigations are the visible "Overridden" badge, the two dates, append-only history, and the ledger-conflict masking warning — deliberately not a second-approval step, which two already-trusted accounts don't warrant, the same reasoning v0.5 applied to letting Ms. K accept a solver proposal herself.
  • The ~0.22pp unexplained gap between the observed 4.625% rate and PayPal's published 4.40% (CLAUDE.md § "Domain model") stays parked and unresolved, per the user's standing direction. This plan must not be read as closing it — an override happens to be able to paper over that gap for display purposes, but that isn't the same as explaining it.
