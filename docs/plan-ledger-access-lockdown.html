Plan · msk_ppal_calc · security fix

Locking the ledger to an allow-list

The v0.5 /ledger gate checked only "is this a valid authenticated session," not "is this one of the two people who should have one." Anyone who knows the app's URL could self-register and read or write the ledger that drives the public calculator's pricing. This is the fix, written up alongside its implementation.

Implemented

The vulnerability

src/proxy.ts gates /ledger* on getClaims() succeeding — a valid session, nothing about identity. src/app/login/actions.ts's requestMagicLink calls supabase.auth.signInWithOtp({ email }) with no shouldCreateUser: false, so any email address self-registers on first request. The on_auth_user_created trigger (supabase/migrations/20260810160000_v0_5_ledger.sql) then unconditionally grants every new auth.users row a profiles row with role='user'. RLS policies on transactions and fee_models only checked to authenticated, not identity: 

create policy "authenticated can read all transactions"
on public.transactions for select to authenticated using ( true );

A stranger could sign in, read the whole ledger, insert fraudulent transactions, and — worse — insert fee_models rows directly, since fee_models INSERT only checked accepted_by = auth.uid(). fee_models's latest row is the active pricing model that drives the public, unauthenticated / calculator and /breakdown client links — a stranger with no relationship to Ms. K could rewrite the numbers every client sees.

Finding — confirmed live, not theoretical

Verified directly: as authenticated with an arbitrary, unknown sub, select count(*) from public.transactions still returned all 3 seeded rows. The policy's using ( true ) meant identity played no role at all in what was readable.

The fix — allow-list enforced at two layers, both in the database

Not in the Next.js app: a server action is a public POST endpoint, and any app-side check can be bypassed by calling Supabase directly with the anon key. The allow-list has to be enforced where the data actually lives.

1. A new table with zero policies

public.allowed_accounts (email text primary key, role text check (role in ('admin', 'user')), note, created_at), RLS enabled with zero policies — deny-all to anon and authenticated — plus an explicit revoke all ... from anon, authenticated, since Supabase's default grants include TRUNCATE, which RLS doesn't cover. Seeded with exactly three rows:

2. The signup trigger rejects anyone not on the list

handle_new_user() (the AFTER INSERT ON auth.users trigger function, SECURITY DEFINER) is rewritten to look up lower(btrim(new.email)) in allowed_accounts. If absent, RAISE EXCEPTION 'account not permitted', which aborts GoTrue's transaction — no auth.users row is created, no session, and critically no magic-link email is ever sent, since GoTrue creates the user row before invoking the mailer. This also protects the project's own email quota (roughly 3/hour) from being burned by a stranger, which would lock out the two real accounts. If present, the trigger inserts profiles(id, role) with the mapped role.

3. Two SECURITY DEFINER helper functions gate the RLS policies

is_ledger_member() and is_ledger_admin(), owned by postgres (which has BYPASSRLS), are used inside RLS policies instead of inlining exists (select 1 from profiles ...) directly. This decouples the policies from profiles' own SELECT policy — the pre-existing admin policy on transactions only worked because profiles' "users can read their own profile" policy happened to expose exactly the row the subquery needed; narrowing that policy later would have silently broken admin UPDATEs to "0 rows affected" with no error anywhere. Both helpers take no arguments, so they're safe to expose as PostgREST RPC — a hypothetical is_allowed(email) would be a public allow-list oracle, which is why the email lookup instead stays inlined inside the trigger, which runs as postgres and needs no grant.

5. Reconcile existing data

Promotes the existing sole account to admin (it wasn't previously admin), and strips profiles rows for anyone not on the allow-list — a no-op today, since the only existing account is being kept, just promoted.

Trap avoided — the crux of the design

A table with RLS enabled but zero policies is not a source you can reference from inside another table's RLS policy. A policy subquery runs as the invoking role, so exists (select 1 from allowed_accounts ...) inside a policy on transactions would always see zero rows — RLS denies the anon/authenticated role reading allowed_accounts itself — and the policy would be unconditionally false, silently locking the ledger for everyone, admin included, with no error anywhere. The fix: never reference allowed_accounts from a policy; policies reference profiles (materialized allow-list membership, written once at signup by the SECURITY DEFINER trigger) via the helper functions instead.

App-layer changes — defense in depth, not the actual security boundary

  • src/lib/auth/profile.ts's getCurrentUser() had a fail-OPEN bug: role: profile?.role === "admin" ? "admin" : "user" returned a valid signed-in CurrentUser even when no profiles row existed — .single()'s zero-row error was silently discarded. Fixed to fail closed: a missing profile now denies access rather than defaulting to role: "user".
  • src/app/login/page.tsx gained an error=no_access message for a signed-in-but-not-allow-listed visitor, with a sign-out button.
  • No change to shouldCreateUser — stays default true, needed so the two new allow-listed accounts can bootstrap. No app-side allow-list duplicate check either — that would reopen the email-enumeration hole the existing generic "check your email" swallow was built to close.

Decision — promote, don't replace

The sole pre-existing account (shrikantkshirsagar29@gmail.com, previously role user) is promoted to admin rather than removed or added as a fourth account — it's the maintainer's own account.

Residual risks — accepted and documented, not fixed

  • Allow-list enforced at account-creation time only. A signed-in allow-listed user could self-serve-change their email via GoTrue's updateUser, keeping access under a different address, since authorization keys off profiles.id, not email. Not fixed: a BEFORE UPDATE ON auth.users re-check would break GoTrue's own email-change flow.
  • The trigger blocks every path into auth.users, including the Supabase Dashboard's own "Add/Invite user" action — adding a fourth person means seeding allowed_accounts first, not just inviting them from the dashboard.
  • An allow-listed account can still insert arbitrary transaction/fee_model data via its own session — unchanged from before this fix; both accounts are trusted.
  • Supabase Auth dashboard settings remain outside version control — this migration governs the schema and RLS, not dashboard-level auth configuration.
