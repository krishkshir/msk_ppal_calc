Plan · msk_ppal_calc · security fix

Locking the ledger to an allow-list

The v0.5 /ledger gate checked only "is this a valid authenticated session," not "is this one of the two people who should have one." Anyone who knows the app's URL could self-register and read or write the ledger that drives the public calculator's pricing. This is the fix, written up alongside its implementation.

Implemented

Revision — the first version cached membership, and never invalidated the cache

Sections 2–5 below originally described writing allow-list membership into a public.profiles row at signup (handle_new_user(), an AFTER INSERT ON auth.users trigger — by definition, one that never fires again for an existing account). A code review run before this PR merged caught the consequence: delete from allowed_accounts did not revoke an existing account's access, and update allowed_accounts set role=... never reached one either — both contradicting this same PR's own CLAUDE.md wording ("adding or removing a person is insert/delete on allowed_accounts"). A sync trigger (write-time invalidation on allowed_accounts) was designed and rejected — a first draft's bare UPDATE instead of an UPSERT silently no-ops once a revoke has deleted the profiles row, permanently locking out anyone re-added afterward, the identical bug shape one level down. Every section below reflects the corrected, shipped design: profiles is gone; membership and role are derived live from allowed_accounts ⋈ auth.users on every call, so there is no cache left to have an invalidation bug. See "Trap avoided" below for why this is also strictly safer than the design it replaced.

The vulnerability

src/proxy.ts gates /ledger* on getClaims() succeeding — a valid session, nothing about identity. src/app/login/actions.ts's requestMagicLink calls supabase.auth.signInWithOtp({ email }) with no shouldCreateUser: false, so any email address self-registers on first request. The on_auth_user_created trigger (supabase/migrations/20260810160000_v0_5_ledger.sql) then unconditionally grants every new auth.users row a profiles row with role='user'. RLS policies on transactions and fee_models only checked to authenticated, not identity: 

create policy "authenticated can read all transactions"
on public.transactions for select to authenticated using ( true );

A stranger could sign in, read the whole ledger, insert fraudulent transactions, and — worse — insert fee_models rows directly, since fee_models INSERT only checked accepted_by = auth.uid(). fee_models's latest row is the active pricing model that drives the public, unauthenticated / calculator and /breakdown client links — a stranger with no relationship to Ms. K could rewrite the numbers every client sees.

Finding — confirmed live, not theoretical

Verified directly: as authenticated with an arbitrary, unknown sub, select count(*) from public.transactions still returned all 3 seeded rows. The policy's using ( true ) meant identity played no role at all in what was readable.

The fix — allow-list enforced at two layers, both in the database

Not in the Next.js app: a server action is a public POST endpoint, and any app-side check can be bypassed by calling Supabase directly with the anon key. The allow-list has to be enforced where the data actually lives.

1. A new table with zero policies

public.allowed_accounts (email text primary key, role text check (role in ('admin', 'user')), note, created_at), RLS enabled with zero policies — deny-all to anon and authenticated — plus an explicit revoke all ... from anon, authenticated, since Supabase's default grants include TRUNCATE, which RLS doesn't cover. 2. The signup trigger rejects anyone not on the list

handle_new_user() (the AFTER INSERT ON auth.users trigger function, SECURITY DEFINER) looks up lower(btrim(new.email)) in allowed_accounts. If absent, RAISE EXCEPTION 'account not permitted', which aborts GoTrue's transaction — no auth.users row is created, no session, and critically no magic-link email is ever sent, since GoTrue creates the user row before invoking the mailer. That protects the project's own email quota (roughly 3/hour) from being burned by a stranger who has never signed up — it does not extend to an address that already has an auth.users row (see "Files changed" and residual risks below: a removed account's row is deliberately left in place). This trigger is now purely a gate — it writes nothing on success, since there's nothing left to write (next section).

3. A single derivation function, not a materialized row

my_ledger_role(), a new SECURITY DEFINER function owned by postgres, joins allowed_accounts to auth.users live, on every call — select a.role from auth.users u join allowed_accounts a on a.email = lower(btrim(u.email)) where u.id = auth.uid() and u.deleted_at is null. is_ledger_member() and is_ledger_admin() — used inside the transactions/fee_models RLS policies, unchanged from before — become one-line wrappers around it (is not null, and coalesce(... = 'admin', false) respectively). All three are zero-argument and report only on the caller, so they're safe to expose as PostgREST RPC — a hypothetical my_ledger_role(email) would be a public allow-list oracle, which is why the account-creation lookup in handle_new_user() stays inlined rather than becoming a callable helper. postgres reads both tables as their owner (exempt from their own RLS) and reads auth.users — owned by supabase_auth_admin, not postgres — via the platform-level rolbypassrls grant already relied on by this migration's reconcile step. A deploy-time guard fails the migration loudly, rather than silently denying every account, if that assumption ever stops holding.

The policies themselves didn't change between v1 and the current design — only what is_ledger_member()/is_ledger_admin() do underneath them did. That's the point of routing policies through named helpers instead of inlining logic directly: the fix for the bug in "Revision" above was a one-file swap, with zero policy edits.

Trap avoided — the crux of the design

A table with RLS enabled but zero policies is not a source you can reference from inside another table's RLS policy. A policy subquery runs as the invoking role, so exists (select 1 from allowed_accounts ...) inside a policy on transactions would always see zero rows — RLS denies the anon/authenticated role reading allowed_accounts itself — and the policy would be unconditionally false, silently locking the ledger for everyone, admin included, with no error anywhere. The fix: never reference allowed_accounts from a policy directly; policies reference the SECURITY DEFINER helper functions, and only my_ledger_role() (running as postgres, exempt from allowed_accounts' RLS as its owner) ever touches the allow-list table itself.

App-layer changes — defense in depth, not the actual security boundary

  • src/lib/auth/profile.ts's resolveUser() now calls the my_ledger_role() RPC instead of querying profiles directly. This fixes two things at once: the original fail-OPEN bug (role: profile?.role === "admin" ? "admin" : "user" returned a valid signed-in user even with no matching row — .single()'s zero-row error was silently discarded; now an explicit not_permitted case denies), and a coupling the original version didn't notice it had — reading profiles through ordinary RLS meant the app's own authorization check depended on profiles' SELECT policy, the exact fragility the SQL-side helpers exist to avoid. An RPC failure is now logged (console.error) rather than silently producing an unexplained redirect loop indistinguishable from being signed out.
  • src/app/login/page.tsx shows a sign-out affordance whenever a session exists and isn't a permitted one — not only via requireUser's ?error=no_access redirect, which a visitor who bookmarks /login directly, or whose access is revoked mid-session, would never hit. Backed by a new hasSession() export (a getClaims()-only check, no RPC) so a merely-unpermitted visitor is distinguished from one who's fully signed out.
  • requireAdmin's non-admin redirect now carries ?error=not_admin, surfaced as a banner on /ledger — previously a silent bounce indistinguishable from an admin-only action having simply had no effect.
  • No change to shouldCreateUser — stays default true, needed so the two new allow-listed accounts can bootstrap. No app-side allow-list duplicate check either — that would reopen the email-enumeration hole the existing generic "check your email" swallow was built to close.

Decision — promote, don't replace

The sole pre-existing account (shrikantkshirsagar29@gmail.com, previously role user) is promoted to admin rather than removed or added as a fourth account — it's the maintainer's own account.

Residual risks — accepted and documented, not fixed

  • The email-quota protection only covers addresses that have never signed up. A removed account's auth.users row is deliberately left in place (see "Decision" in the migration — deleting it is a separate, irreversible action taken by hand), and handle_new_user() only fires on insert. So a removed-but-still-existing account can still call signInWithOtp successfully — no insert, no trigger, email sent — even though it can no longer read or write anything once signed in (membership is re-checked live on every request). Three such requests exhaust the project-wide hourly cap.
  • The trigger blocks every path into auth.users, including the Supabase Dashboard's own "Add/Invite user" action — adding a fourth person means seeding allowed_accounts first, not just inviting them from the dashboard.
  • An allow-listed account can still insert arbitrary transaction/fee_model data via its own session — unchanged from before this fix; both accounts are trusted.
  • Supabase Auth dashboard settings remain outside version control — this migration governs the schema and RLS, not dashboard-level auth configuration.
  • The hot path now depends on postgres retaining read access to auth.users for every ledger request, not just the rare account-creation path — see "A single derivation function" above and its deploy-time guard.

Closed, not merely accepted, by this revision: an allow-listed user changing their own auth email via GoTrue's updateUser used to keep access under the new address (authorization keyed off the stable profiles.id). It now keys off live auth.users.email, so that move self-revokes immediately, fail-closed.
