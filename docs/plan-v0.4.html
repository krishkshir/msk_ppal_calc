Plan · msk_ppal_calc · v0.4

Implementing v0.4: broader currency and market coverage

Proposal for the fourth roadmap milestone in docs/CONSTITUTION.md — fee-table refresh workflow, broader currency and buyer-market coverage, and resolving the open question this project can actually resolve.

Proposed

Scope

v0.1 built the engine, v0.2 built Ms. K's own calculator, v0.3 built the artifact she sends a client. All three shipped against a deliberately narrow slice: two currencies (USD, CAD) and a fixed-fee model that derives every non-USD fee by converting the observed USD figure at the FX rate, rather than using PayPal's own published per-currency table. The roadmap names v0.4 as the milestone that widens both:

v0.4 — Fee-table refresh workflow; broader currency and buyer-market coverage; resolve the open questions above.

Three scope decisions were confirmed with the user before drafting this plan:

  • Currencies. All 22 currencies that appear in both PayPal's published fixed-fee table and Frankfurter's rate list — including JPY, which has no minor decimal unit and forces the codebase's hardcoded "divide by 100" assumption to become real.
  • Buyer market. A country picker that maps a selected country to the correct PayPal market bucket, rather than asking Ms. K to classify UAE / EEA & UK / all other markets herself.
  • Refresh workflow. A written checklist, review-date metadata on the schedule, and a staleness note surfaced in the calculator UI when a review is overdue.

Of CONSTITUTION.md's two still-open questions, v0.4 resolves only the first — the fixed-fee table for non-USD currencies. The second (the unexplained ~0.22pp gap between the observed 4.625% rate and PayPal's published 4.40% figure) stays parked at the user's direction; nothing in this plan touches the commercial rate itself.

Explicitly out of scope, per the roadmap's own sequencing:

  • v1.0+ — PayPal API reconciliation against real seller_receivable_breakdown data.
  • Re-deriving or re-validating the commercial rate/tier percentages themselves — every ScheduleEntry.rate is untouched by this plan.
  • Any resolution of open question #2 above.

One source of truth for currencies and markets

Today Currency and BuyerMarket are bare unions in src/lib/fees/types.ts, but two other files hand-duplicate them as runtime arrays with no compile-time link: src/lib/share/breakdown-link.ts's CURRENCIES / BUYER_MARKETS guard arrays, and src/components/calculator-form.tsx's CURRENCIES / BUYER_MARKETS dropdown option lists. This was already flagged as a v0.4 hazard in docs/CHANGELOG.md when v0.3 shipped: going from 2 currencies to 22 without fixing it would silently reject valid share links for every currency added after the fact, with no type error to catch it.

Finding — three independent enumerations of the same two unions

types.ts (the union), breakdown-link.ts (a runtime validation array), and calculator-form.tsx (a UI option list) each currently list "USD" | "CAD" and the three buyer markets separately, by hand. None derives from another.

v0.4 inverts the relationship — arrays become the source of truth, and the unions derive from them:

// src/lib/fees/currencies.ts — imports nothing, so no import cycle
export interface CurrencySpec {
  code: string;
  label: string;
  minorUnitExponent: 0 | 2;       // JPY is 0; every other currency here is 2
  fixedFeeMinorUnits: number;
  confidence: Confidence;
  effectiveFrom: string;
  sourceUrl: string;
  note?: string;
}
export const CURRENCIES = [ /* 22 entries, see next section */ ] as const;
export type Currency = (typeof CURRENCIES)[number]["code"];
export function currencySpec(code: Currency): CurrencySpec;
export function isCurrency(value: unknown): value is Currency;

// src/lib/fees/markets.ts
export const BUYER_MARKETS = ["UAE", "EEA_UK", "OTHER"] as const;
export type BuyerMarket = (typeof BUYER_MARKETS)[number];
export interface CountrySpec { code: string; name: string; market: BuyerMarket; defaultCurrency: Currency; }
export const COUNTRIES: CountrySpec[] = [ /* see "Country picker" below */ ];
export function marketForCountry(countryCode: string): BuyerMarket;
export function isBuyerMarket(value: unknown): value is BuyerMarket;

src/lib/fees/types.ts re-exports Currency and BuyerMarket from these two new modules, so no existing import path (from "@/lib/fees/types") changes anywhere in the codebase. breakdown-link.ts and calculator-form.tsx are updated to consume CURRENCIES / COUNTRIES from the new modules instead of their own hand-written copies.

Finding — two pinned test literals will change

breakdown-link.test.ts currently asserts the exact rejection strings "cur must be one of USD, CAD" and "mkt must be one of UAE, EEA_UK, OTHER". Once the list is derived from CURRENCIES/BUYER_MARKETS, those tests must assert the derived string (built via .join(", ") over the new arrays) rather than a hardcoded literal, or they'll fail the moment a currency is added.

The fixed fee stops being FX-derived

This is the substance of the open question v0.4 resolves. Today engine.ts's resolveFixedFeeCents estimates any non-USD fixed fee by converting the observed USD figure through the FX rate: roundHalfUpCents(fixedFeeUSDCents / fxBaseRateToUSD). That's a documented estimate, not a lookup — and CONSTITUTION.md already has PayPal's actual published per-currency fixed-fee table sitting unused (§ "Fixed fee by currency (published)").

Decision — look the fixed fee up by currency, stop deriving it from FX

fixedFeeUSDCents is removed from ScheduleEntry in src/lib/fees/schedule.ts — PayPal's fixed fee varies by currency, not by market or volume tier, so keeping it on the tier misrepresented the structure. The commercial fee's fixed component becomes currencySpec(payCurrency).fixedFeeMinorUnits, looked up directly, with no FX conversion involved at all.

USD keeps its observed $0.31, not PayPal's published $0.30 — this is the exact correction CONSTITUTION.md's T1–T3 analysis already established, and nothing about broadening currency coverage should regress it. A PUBLISHED_USD_FIXED_FEE_MINOR_UNITS = 30 constant stays alongside it in currencies.ts so the refutation remains visible in code, not just in the docs. Every other currency takes PayPal's published figure verbatim — not scaled by the observed/published USD ratio (1.033), which would invent data no transaction has confirmed.

Two currencies in that same published table — TWD and RUB — are dropped: Frankfurter/ECB has no rate for either, and the FX module has no other rate source, so neither could ever be settled or quoted regardless of the fixed-fee table.

Finding — the moot volume tiers pick up the correction too

The three unvalidated OTHER-market volume tiers above $3,000 currently carry fixedFeeUSDCents: 30; once the fixed fee is a currency lookup, a USD payment in any of those tiers picks up $0.31 instead. This is a real, stated consequence of the change, not a silent one — but it's inert in practice, since CONSTITUTION.md already confirms Ms. K doesn't qualify for merchant-tier rates and her practical tier is always the $0–$3,000 row.

confidenceFor in engine.ts is unchanged — a non-USD commercial fee still reports estimated overall (an observed rate combined with a published-but- unobserved fixed fee is still not fully observed). Only the line item's note text changes, from "the fixed fee is estimated by converting the USD figure" to "the fixed fee is PayPal's published <currency> figure, unvalidated by observation."

Finding — the Canadian regression locks move, deliberately

engine.test.ts's "README's Canadian scenario" test locks CAD 1,000.00 at 0.73 USD/CAD to commercialFee 4667 / fxConversion 2784 / received 66_809, built on today's FX-derived CAD fixed fee of 42 cents (round(31 / 0.73)). With the published CAD fixed fee of 30 cents used directly, the same inputs produce commercialFee 4655 / fxConversion 2784 / received 66_818 — nine cents more lands in Ms. K's account, because 30 CAD cents is a smaller deduction than the FX-inflated 42. This test's assertions must be updated to the new numbers as part of this change, with the arithmetic shown in the commit, not silently "fixed."

Minor units, because JPY has none

src/lib/format.ts divides by a literal 100 in three places, and Money.cents / FeeLineItem.cents name the unit "cents" throughout the engine. JPY has no minor decimal unit at all — PayPal's published ¥40.00 fixed fee is 40 yen, not 0.40 — so every one of those assumptions breaks the moment JPY is added.

FileChange
src/lib/fees/types.tsMoney.cents → Money.minorUnits; FeeLineItem.cents → FeeLineItem.minorUnits. Fields that are always USD (netTargetCents, minMonthlyVolumeUSDCents) keep their name — the name should state the unit, and those never vary by pay currency.
src/lib/fees/money.tsroundHalfUpCents → roundHalfUp; behavior unchanged (Math.floor(x + 0.5)).
src/lib/format.tsformatMoney(minorUnits, currency) and formatAmount(minorUnits, currency) build the Intl.NumberFormat and the divisor from currencySpec(currency).minorUnitExponent instead of a hardcoded 2 and 100. formatAmount gains a required currency parameter — its two call sites (fee-breakdown.tsx's fee row and its converted-to-USD row) already know which currency they're formatting. parseDollarsToCents → parseAmountToMinorUnits(input, currency), same exponent-aware treatment on the way in.

Decision — share links keep decoding, only the TS field name changes

The share URL's query-param keys (gross, cur, mkt, sched, fx, on) and the integer-minor-unit encoding are untouched by this rename — gross was always "smallest unit of the currency," which already meant something different for a currency with a different exponent. A v0.3-era link is still valid input to the v0.4 decoder. Only SharedBreakdown's in-memory field name changes to match the engine.

Country picker for buyer market

The three buyer-market buckets already cover PayPal's whole schedule — nothing about the bucket set itself changes. What changes is how Ms. K picks one: today's dropdown asks her to know PayPal's classification directly ("UAE" / "EEA & UK" / "All other markets"). A country picker instead asks the question she actually knows the answer to — where the client is — and the app does the classification.

calculator-form.tsx gains a country <select>, styled identically to the two existing native selects (this repo deliberately hand-rolls form controls rather than pulling in a shadcn Select — see docs/plan-v0.3.html § "The share affordance"). The resolved market stays visible underneath as a caption, e.g. "PayPal market: EEA & UK," so the mapping is auditable rather than hidden behind the picker. 

src/lib/fees/markets.ts

COUNTRIES: CountrySpec[] =
  UAE                                              → market: "UAE"
  EU-27 + Iceland, Liechtenstein, Norway, UK        → market: "EEA_UK"
  every country whose currency is in CURRENCIES,
    plus an explicit "Other / not listed" entry     → market: "OTHER"

Selecting a country pre-fills that country's usual currency (defaultCurrency); Ms. K can still override the currency, since a client anywhere may choose to pay in USD.

Finding — the exact classification trap a picker exists to prevent

Switzerland is not in the EEA — it's EFTA, a separate bloc — so a Swiss client maps to "OTHER" at 4.625%, not to the EEA/UK bucket at 4.69%. That's a genuinely easy mistake to make by hand (Switzerland is geographically and economically "basically EU" to most people), and it's precisely the kind of error an abstract three-bucket dropdown invites and a country-name picker resolves by construction — Ms. K never has to know the EEA's actual membership list.

Fee-table refresh workflow

docs/plan.html's "Maintenance contract" already committed to a quarterly review against PayPal's published schedule; nothing in the codebase enforces or even surfaces that commitment today. v0.4 makes staleness visible instead of silent — the exact failure mode that section calls out as the one to avoid.

  • New docs/FEE-TABLE-REFRESH.md — a checklist: re-read the two PayPal source pages (merchant fees, business fees), diff the market rates / per-currency fixed fees / the 4.0% MEA spread against what's in schedule.ts and currencies.ts, how to append a newly observed transaction (both CONSTITUTION.md's table and docs/plan.html, per this project's existing dual-doc convention, plus a named regression test in engine.test.ts), and which dates to bump.
  • src/lib/fees/schedule.ts gains SCHEDULE_LAST_REVIEWED_ON and REVIEW_INTERVAL_DAYS = 92, plus a pure isScheduleReviewOverdue(today: Date): boolean.
  • Surfaced on src/app/page.tsx only — Ms. K's own calculator view. Deliberately not added to src/components/fee-breakdown.tsx, which src/app/breakdown/page.tsx also renders for clients: a client has no use for, and shouldn't see, Ms. K's internal maintenance state.
  • Tests — boundary cases for isScheduleReviewOverdue, and an extension of the existing "schedule metadata" test in engine.test.ts so every entry in CURRENCIES (not just SCHEDULE) carries a well-formed effectiveFrom, a non-empty sourceUrl, and a valid confidence.

Known limitations to record, not hide

  • FX precision thins out for low-unit currencies. Frankfurter returns JPY→USD to roughly three significant figures (e.g. 0.00632) — about 0.1% of slack on a JPY settlement. Acceptable for a figure already labeled an estimate; recorded here rather than discovered later.
  • 21 of the 22 non-USD fixed fees remain unvalidated by observation. v0.4 resolves open question #1's sourcing — using PayPal's own published table instead of an FX-derived guess — not its validation. The USD row's own $0.30-published-vs-$0.31-observed gap is the standing proof that a published figure can still be off by a cent; nothing here claims otherwise for the other 21.
  • src/lib/fees/errors.ts's string-matching against engine error messages is pre-existing and unrelated to this change — not touched.
